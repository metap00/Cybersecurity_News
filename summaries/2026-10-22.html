Critical GitLab Flaw (CVE-2026-110264, CVSS 10.0) Enables Unauthenticated RCE Across Every Version Back to 2014
🔍 What happened: GitLab released an emergency security update fixing CVE-2026-110264, a CVSS 10.0 vulnerability in the CI/CD pipeline engine that allows an unauthenticated attacker to execute arbitrary code on any self-managed GitLab server running versions all the way back to 7.0 (released in 2014).
👤 Who's affected: All self-managed GitLab Community Edition and Enterprise Edition installations that haven't yet updated — GitLab.com (the hosted service) was already patched automatically.
✅ What to do: Update self-managed instances to GitLab 19.4.2, 19.3.5, or 19.2.8 immediately; place self-managed instances behind a VPN or restrict public internet access until the patch is applied.
🎯 ATT&CK: [Initial Access] T1190 · Exploit Public-Facing Application
A CVSS 10.0 unauthenticated RCE on GitLab's public-facing web interface gives attackers direct server access with no prior foothold, enabling immediate theft of source code, secrets, and CI/CD pipeline credentials for all hosted repositories.
▶ Full analysis & beginner explanation

The vulnerability is an integer overflow in GitLab's CI/CD regular expression compiler. An attacker can craft a specially formed input to trigger the overflow, which bypasses size validation checks and allows arbitrary code execution on the server. The CVSS 10.0 score — the maximum possible — reflects that exploitation requires no authentication, no user interaction, and works across an enormous range of deployed versions.

The blast radius is particularly concerning because GitLab self-managed instances are typically the central nervous system of a software development organisation: they contain source code, deployment scripts, environment variables, API tokens, and cloud credentials. A compromised GitLab server provides an attacker with everything needed to pivot into cloud infrastructure, poison CI/CD pipelines with backdoored builds, and access every project in the organisation simultaneously.

GitLab.com is already patched and unaffected. The risk falls entirely on organisations running their own GitLab servers who haven't updated — CERT-EU issued an advisory strongly recommending immediate patching of internet-facing instances.

🎓 For beginners: GitLab is like GitHub but self-hosted — companies run it on their own servers to store their code privately. This bug means a hacker can visit your company's GitLab web address and, without even having a username, take full control of the server, stealing every line of code and every secret your development team has ever stored there.

👤 Who's affected: Critical infrastructure operators globally — energy, healthcare, financial services, and government sectors — particularly those running unpatched VPN appliances or exposed Veeam backup servers.
✅ What to do: Patch all edge devices and VPN appliances immediately (especially CVE-2020-3259 and CVE-2023-20269 in Cisco gear), enforce MFA across all remote access, restrict admin tools like WinSCP and RClone to authorised users, and maintain offline/air-gapped backups since SafePay specifically destroys VSS shadow copies and NAS backup devices.
🎯 ATT&CK: [Impact] T1490 · Inhibit System Recovery
SafePay's most distinctive TTP is the deliberate destruction of VSS shadow copies and resetting of NAS backup devices before deploying encryption, ensuring victims cannot recover without paying the ransom — a calculated move that maximises leverage.
▶ Full analysis & beginner explanation

SafePay operates as a financially motivated criminal ransomware group first observed in August 2024. The advisory reveals a sophisticated playbook: attackers begin by exploiting known vulnerabilities in edge devices and VPN appliances to gain initial access, then use entirely legitimate administrative tools — FileZilla, 7-Zip, WinRAR, WinSCP, RClone — for lateral movement and data exfiltration. This "living off the land" approach makes detection significantly harder since security tools see normal admin utilities rather than obvious malware.

The backup-destruction phase is particularly notable. SafePay actors locate and delete Windows Volume Shadow Copies (VSS snapshots), then factory-reset any network-attached storage devices used for backups before deploying their encryptor. CISA explicitly warns that paying the ransom does not guarantee file recovery — this is consistent with a trend of ransomware actors taking payment while still withholding working decryption keys or having already destroyed data beyond recovery.

At 600+ confirmed victims across critical sectors, SafePay has established itself as a top-tier ransomware threat. The advisory comes with 19 specific MITRE ATT&CK technique mappings, indicating a mature and disciplined operation with consistent TTPs across victims.

It's like a thief who burns your spare keys before demanding money to return yours.

✅ What to do: If you installed LiteLLM between 11:39 and 13:40 UTC on October 21, treat all secrets accessible to any Python process on that machine as compromised — rotate every API key, cloud credential, and access token immediately; remove the malicious package and follow LiteLLM's remediation guidance.
🎯 ATT&CK: [Initial Access] T1195.001 · Supply Chain Compromise: Compromise Software Dependencies and Development Tools
By inserting malicious code into LiteLLM's PyPI package, attackers compromised every downstream AI deployment that pip-installed the package during the window — a supply chain attack that bypasses all endpoint security by hiding in trusted software.
▶ Full analysis & beginner explanation

The malware uses a particularly sophisticated persistence mechanism: a Python path file (.pth file placed in site-packages) that causes malicious code to execute every time the Python interpreter starts — not just when LiteLLM is imported. This means even running an unrelated Python script on a compromised machine triggers the stealer.

The credential stealer targets the exact assets most valuable in AI-infrastructure environments: LiteLLM proxy saved credentials, model configuration, OpenAI/Anthropic/Google AI API keys, cloud provider credential JSON files (AWS, GCP, Azure), private keys stored on disk, and Chromium/Firefox browser profile data including saved passwords and session cookies. The backdoor component forks a background daemon that checks a GitHub repository (used as a "dead drop" C2 channel) every hour, executing whatever Python code the attacker serves.

This is the second LiteLLM supply chain compromise in 2026 — a March attack via stolen PyPI tokens affected versions 1.82.7 and 1.82.8. The October attack was enabled by GitHub CLI OAuth tokens stolen from three contributors' accounts. The malicious package and Docker images have since been removed, but any environment that installed during the window should be treated as fully compromised.

💡 Today I Learned: Supply Chain Poisoning ▶
Supply chain poisoning is an attack where adversaries compromise software packages, build systems, or distribution channels used by developers rather than attacking end users directly — when thousands of organisations install the same backdoored library, the attacker compromises them all at once without ever touching each victim's network. Today's LiteLLM and OVHcloud incidents are textbook examples: one compromised contributor account or one tampered package release creates a single point of infection that propagates silently to every downstream user who runs pip install or downloads a release archive. Defending against it requires verifying software signatures and checksums, pinning dependency versions, and monitoring for unexpected credential exfiltration rather than relying solely on perimeter defences.
📖 Glossary: PyPI · Shadow Copy · NAS · Dead Drop · MITRE ATT&CK · Integer Overflow ▶
PyPI — The Python Package Index; the official repository from which Python developers install software packages using the pip install command, making it a high-value target for supply chain attacks.
Shadow Copy — A Windows Volume Shadow Copy Service (VSS) feature that automatically creates point-in-time snapshots of files, providing a built-in recovery option; ransomware actors routinely delete shadow copies to prevent victims from restoring data without paying.
NAS — Network-Attached Storage; a dedicated file-storage device connected to a network and used by organisations for centralised backups, frequently targeted by ransomware actors who reset or encrypt NAS devices to destroy recovery options.
Dead Drop — A covert command-and-control technique where malware retrieves instructions from a public resource (like a GitHub page or Pastebin post) rather than connecting directly to an attacker's server, making C2 traffic harder to detect and block.
MITRE ATT&CK — A globally accessible knowledge base maintained by MITRE Corporation that catalogues real-world adversary tactics, techniques, and procedures (TTPs) using a standardised taxonomy, widely used by defenders to classify attacks and map detection coverage.
Integer Overflow — A programming error that occurs when an arithmetic operation produces a value too large to be stored in its allocated variable, causing it to wrap around to an unexpected (usually very small or negative) number; exploited by attackers to bypass size checks and corrupt memory, as seen in today's GitLab CVE-2026-110264.
