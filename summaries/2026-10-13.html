GitLab Issues Emergency Patches for CVSS 10.0 CI/CD Regex Compiler RCE
🔍 What happened: GitLab disclosed CVE-2026-97229, a CVSS 10.0 integer overflow in its CI/CD regular expression compiler that allows unauthenticated attackers to execute arbitrary code on self-managed GitLab servers via a crafted regex in a pipeline configuration file.
👤 Who's affected: Organizations running self-managed GitLab CE/EE versions 19.2.x, 19.3.x, or 19.4.x; GitLab.com and Dedicated customers are already patched and require no action.
✅ What to do: Upgrade immediately to GitLab 19.4.2, 19.3.4, or 19.2.8; internet-facing instances should be treated as highest priority and temporarily firewalled if patching is delayed.
🎯 ATT&CK: [Initial Access] T1190 · Exploit Public-Facing Application
A crafted regex submitted to the CI/CD API triggers an integer overflow in GitLab's bundled Ruby runtime, bypassing bounds checks and achieving unauthenticated remote code execution on the server without any login or project membership.
▶ Full analysis & beginner explanation

GitLab's emergency patch release addresses one of the most severe vulnerabilities discovered in developer tooling this year. The flaw resides in the Regular Expression Compiler used to parse .gitlab-ci.yml pipeline configurations — the same files that control automated build, test, and deployment workflows for millions of software projects worldwide.

An attacker who can reach the GitLab server's HTTP API needs only to submit a specially crafted regex pattern to trigger an integer overflow (CWE-190) in the underlying Ruby runtime that GitLab bundles. Because regex evaluation happens before any authentication checks, no login or project membership is required. The overflow corrupts memory in a way that redirects execution to attacker-controlled code.

GitLab.com was patched silently before disclosure, but the roughly 30% of organizations running self-managed installations face real exposure. Exploitation requires only network access — firewalled internal installations behind a VPN are far less exposed than internet-facing ones. No public proof-of-concept existed at disclosure, but the detailed advisory and prior bugs in the same component give skilled attackers a clear map. Researcher joaxcar discovered the flaw through GitLab's HackerOne bug bounty program.

🎓 For beginners: GitLab is a platform developers use to store code and run automated software-building tasks. A regex is a pattern used to search or validate text. This bug is like a trick calculation where a too-big number wraps around to zero and tricks the computer into running the attacker's code — with no password needed. If your company uses a self-managed GitLab server, treat this as a fire drill.
CVE-2026-97229 · CVSS: 10.0/10 — Maximum score; network-accessible, zero-authentication exploitation with full server compromise potential (C:H/I:H/A:H).

GhostAction Campaign Plants Credential-Stealing Workflows in 10,000+ GitHub Repositories
🔍 What happened: Attackers compromised 500+ GitHub maintainer accounts since October 7 and used them to plant malicious GitHub Actions workflow files (named security-audit.yml) that silently exfiltrate cloud credentials, AI API keys, and repository secrets to an attacker-controlled server.
👤 Who's affected: Open source maintainers and organizations with contributors whose GitHub accounts were compromised; any repository containing the planted workflow file is actively leaking credentials on every code push.
✅ What to do: Audit recent workflow file changes for unexpected security-audit.yml files, immediately rotate all GitHub Actions secrets, AWS keys, and AI API tokens, and review your git history for any previously committed credentials.
🎯 ATT&CK: [Credential Access] T1552.004 · Unsecured Credentials: Private Keys
Malicious workflow files silently collect repository secrets, cloud API keys (AWS, Anthropic, OpenAI), and OAuth tokens from the CI/CD environment and full git history, exfiltrating everything over HTTP to a hard-coded attacker IP address (193.32.204.199).
▶ Full analysis & beginner explanation

GhostAction represents a sophisticated supply chain attack exploiting the trust relationships between developers and their automated tools. The attackers first compromised legitimate, well-known maintainer accounts — including contributors to popular projects like Uber's athenadriver and the Pyxel game engine — then used those trusted identities to push a file named security-audit.yml to hundreds of repositories in a single evening.

The filename is deliberately chosen to mimic a legitimate security scanning workflow, blending into the automated pipelines developers run daily without raising suspicion. Once merged, the workflow executes silently on every code push, harvesting: GitHub Actions secrets (including GITHUB_TOKEN and AWS_ACCESS_KEY_ID), credentials stored anywhere in the repository or its full git history, and API keys for AI services including Anthropic, OpenAI, and OpenRouter. All stolen data is transmitted in plaintext to 193.32.204.199.

Scale grew rapidly: on October 8, two seed accounts pushed to 27 and then 318 repositories in a 16-minute window. Socket has since tracked more than 500 compromised accounts and tens of thousands of affected repositories. The campaign links to GhostAction activity first documented in September 2025. How attackers initially obtained the maintainers' credentials remains unknown.

🎓 For beginners: GitHub Actions are automated robots that run when developers push code — like a conveyor belt that automatically tests and packages software. The attackers inserted a fake "security check" robot into thousands of projects; instead of checking security, it quietly copied all the passwords and API keys and sent them to the criminals.
No CVE — supply chain attack via compromised developer accounts; credential theft scope includes cloud, AI platform, and source control credentials.

Bricksforge WordPress Plugin CVE-2026-85097 Exploited in Wild — Third Critical Bug in Five Weeks
🔍 What happened: A CVSS 9.8 unauthenticated arbitrary file upload vulnerability (CVE-2026-85097) in the Bricksforge WordPress plugin is being actively exploited since October 7, allowing attackers to upload malicious PHP files and execute arbitrary code on victim websites.
👤 Who's affected: WordPress websites running Bricksforge plugin version 3.1.8.9 or earlier — this is a paid premium plugin used for advanced form building and page customization on top of the Bricks page builder.
✅ What to do: Update Bricksforge to version 3.1.8.10 or later immediately; scan your WordPress upload and plugin directories for unexpected PHP files; review server logs for suspicious POST requests to form endpoints since October 7.
🎯 ATT&CK: [Initial Access] T1190 · Exploit Public-Facing Application
Insufficient validation of the attacker-controlled temporaryFileUploads parameter in form submissions allows unauthenticated HTTP POST requests to write arbitrary PHP files to the web server's document root, enabling immediate remote code execution.
▶ Full analysis & beginner explanation

Bricksforge is a premium add-on for the Bricks page builder, used by WordPress site owners to create advanced forms, animations, and custom interactive elements. The vulnerability is rooted in how the plugin handles file uploads through its form component: the temporaryFileUploads parameter accepts a URL without validating the file type or verifying the requester's identity (CWE-434).

This lets an unauthenticated attacker POST a request pointing to a remote PHP script, which the plugin downloads and stores in the web server's publicly accessible directory. The attacker can then navigate to that URL and execute arbitrary server-side commands — effectively owning the web server. Patchstack observed exploitation beginning October 7 at 21:47 UTC.

Critically, this is the third serious vulnerability in Bricksforge within five weeks, indicating a pattern of inadequate security review in the codebase. Even after patching, previously uploaded webshells may persist in upload directories — a full cleanup audit is required alongside the update. Patchstack's virtual patching rules provide a temporary shield for customers who cannot immediately update.

🎓 For beginners: WordPress powers about 40% of all websites, and plugins add extra features. This bug is like a mailbox that accepts any package without checking contents — attackers send a package containing a remote-control program, and once it's delivered to the website's files, they can run any command on that server.

💡 Today I Learned: Integer Overflow ▶
An integer overflow happens when a computer program tries to store a number that is too large for the memory slot it allocated, causing the value to silently "wrap around" — like a car odometer that clicks back to 00000 after reaching 99999. In software security, attackers deliberately trigger these overflows by feeding programs extreme input values, causing the program to miscalculate the size of memory regions and skip safety checks — this is the classic path to buffer corruption and ultimately arbitrary code execution. Today's GitLab vulnerability (CVE-2026-97229) is a textbook example: a crafted regex pattern causes the CI/CD parser's internal counter to overflow its bounds, corrupting memory in a way that lets an unauthenticated attacker redirect execution to their own code.
📖 Glossary: GitHub Actions · CI/CD · Botnet · HIPAA · PHI ▶
GitHub Actions — Automated workflow scripts that run inside GitHub repositories when code events occur (like a push or pull request), used for testing, building, and deploying software.
CI/CD — Continuous Integration/Continuous Delivery: the practice of automatically building, testing, and deploying software every time developers commit code changes, enabling faster and more reliable software releases.
Botnet — A network of computers silently infected with malware and remotely controlled by a threat actor without the owners' knowledge, used to launch coordinated attacks, proxy malicious traffic, or mine cryptocurrency.
HIPAA — Health Insurance Portability and Accountability Act: U.S. federal law requiring healthcare organizations to protect the privacy and security of patient health information and notify affected individuals of data breaches.
PHI — Protected Health Information: individually identifiable health data — such as diagnoses, treatment records, and test results — that is legally protected under HIPAA when held by a covered healthcare entity or its business associates.
